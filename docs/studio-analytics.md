# Studio analytics

Open https://akogarecafe.com/dashboard (the GitHub Pages entry redirects to the existing hash router). The exact `akogarecafe.com` domain is authorized for Firebase Google sign-in, alongside the existing movieclub domain; the original domains were preserved.

Google workspace sign-in continues in the same tab at `https://ac-movie-club.firebaseapp.com/#/dashboard`. The dashboard is also hosted there, with its existing Firebase `authDomain` matching the page origin. This avoids the stalled cross-window callback observed in Chrome and the cross-origin storage dependency of redirect sign-in. The app handles `getRedirectResult` on return; it does not pass tokens through URLs. Both hosts call the same protected reporting function. Email/password login remains available on the cafe host.

The public site contains an empty dashboard shell. All shared reports require a Firebase ID token. The `projectAnalytics` callable checks the verified email against `allowedEmails` in the `AKOGARE_ANALYTICS_CONNECTIONS` Secret Manager secret, or a trusted `dashboardViewer` custom claim, before fetching or returning cached data. A legacy Gmail account with an unverified Firebase primary email must instead have a fresh Google sign-in: the function checks the token's Google subject against the server-side Google provider identity and its exact invited Gmail address. An unverified email or password sign-in alone never grants access. A Firestore user document cannot grant dashboard access. Only the owner's two existing Google accounts were initially allowlisted. Add invited readers deliberately through the secret or a server-admin custom claim; never broaden this to all authenticated accounts.

Provider credentials are stored only in that Firebase secret. No provider tokens, member records, private report snapshots or service-account keys belong in Git or static assets. Browser reporting OAuth uses a separate Firebase auth instance, so selecting a YouTube Brand Account does not replace the workspace login. Its transient redirect state uses tab-session storage and is cleared immediately on return, including the secondary Firebase session. The resulting Google access token and reports stay in memory and clear at sign-out, account change or page reload. Google reporting uses the same-tab redirect flow as workspace sign-in; another reporting redirect also ends previous in-memory reporting connections. A Google Analytics token can be reused for the website and iOS source selectors during that page session. The separately authorized server connections provide automatic reporting across visits; browser consent remains a temporary fallback.

The server also supports independently approved automatic Google reporting connections. `googleReportingClient` holds a dedicated OAuth client in the dashboard's Google project, `ga4OAuth` holds its Analytics refresh connection, and `youtubeReporting` holds channel-specific refresh connections. These take precedence over the older YouTube connections without editing or replacing publishing credentials. Provision them only after explicit consent to persistent read-only access. Use authorization code flow with PKCE, a random state checked on return, and a loopback callback for the desktop client. Validate the exact read-only scopes and the expected property/channel before saving a connection. Keep callback codes and tokens out of URLs printed in logs, source files, browser storage and static assets. When accessing Secret Manager directly, omit request and response bodies from diagnostic logging.

The Analytics connection requests only `analytics.readonly`. Each YouTube activity connection requests `youtube.readonly` and `yt-analytics.readonly`. Separately approved earnings connections also request `yt-analytics-monetary.readonly`; publishing or editing scopes are not needed. The function refreshes each connection once per reporting request, shares the Analytics token across its mapped sources, and returns only report data plus an `automatic` connection marker. The source details explain automatic reporting only when the server confirms that connection. A failed YouTube period report retains freshly fetched channel totals as limited access, with the period metrics unknown. After changing the secret, deploy the isolated function again so it uses the new version, then verify reports after a fresh signed-in page load.

## Reporting semantics

Dates cover 1, 7, 28 or 90 completed UTC calendar dates, ending yesterday. The default is 28 days. Last 1 day is yesterday’s calendar date, not a rolling 24-hour or realtime report; its chart uses a centered point. A visible notice explains that daily numbers are provisional and YouTube can take 48–72 hours to process. Empty one-day YouTube reports keep period metrics unknown and show a waiting state while preserving current channel totals; explicit reported zeroes remain zero. Weekly and 28-day views are more useful for judging trends. Providers apply their own property/reporting timezone to those dates; cross-provider day boundaries may differ. YouTube and Instagram content views are separate from Pinterest impressions, website sessions, iOS active users and lifetime totals. The activity chart initially chooses a metric with available daily reports, falls back to a metric for the selected platforms when data is still collecting, and preserves an explicit user choice. A collecting source has matching visible and accessible empty-chart messages. Points use actual calendar spacing within the selected reporting period. A configured collection start date bounds requests and suppresses unavailable prior-period comparisons; periods ending before collection starts have no fabricated zero metrics. Missing values remain null/unknown; true zero remains zero. Coverage labels identify partial totals. Audience counts are a sum of channel followers/subscribers, not deduplicated people. Comparisons appear only with complete current and previous coverage. The backend has a five-minute, authorized-workspace cache. The page refreshes while visible, independently retains errors, and clearly marks retained data stale on failure. A date/account change clears old period data.

CSV exports contain only the visible sources' available metrics and are generated on an explicit click. Snapshot metrics have blank period dates. No private export is uploaded to the repository.

## Server deployment

`firebase.analytics.json` defines an isolated `akogare-analytics` codebase. Deploy only that codebase to `ac-movie-club`; do not deploy/delete the existing club functions. Runtime: Node 22, first generation, us-central1, maximum three instances, 60-second timeout. The caller endpoint is fixed in `src/components/Dashboard/api.js`.

Install server libraries with `npm ci --prefix analytics-functions`, test with `npm test --prefix analytics-functions`, and deploy with `firebase deploy --config firebase.analytics.json --only functions:akogare-analytics --project ac-movie-club --non-interactive`. Secrets are configured separately with the supported Firebase CLI stdin mechanism; never put their values in command arguments or tracked files.

The site's normal `main` branch workflow tests and publishes the client to GitHub Pages. Publish the same tested build to the secure workspace with `firebase deploy --config firebase.analytics.json --only hosting --project ac-movie-club --non-interactive`. The Firebase hosting site had no deployed public app before this dashboard. Its pages have an `X-Robots-Tag: noindex, nofollow` header. Changing server source also requires the separate Firebase functions deployment above. A Git push alone does not update the function or Firebase-hosted client.

## Period changes

Summary cards, project cards and channel rows show signed count changes and percentages versus the previous equal-length period. Each change uses only sources with both current and previous metrics; partial comparison coverage is labelled separately from total-metric coverage. A zero baseline still shows the absolute change but no undefined percentage. Stale or failed sources never contribute a change. Lifetime totals never receive period comparisons. YouTube audience growth is subscribers gained minus lost during the reported days, not a difference between rounded subscriber snapshots. Product account growth counts creation timestamps within the selected dates; it describes new accounts, not net growth after deletions.

Daily audience history is stored server-side in `_studioAudienceHistory/{sourceId}`, only after workspace authorization and a successful fresh provider fetch. A transaction keeps the latest observation per UTC date, including decreases and genuine zeroes; an older or concurrent response cannot overwrite a later observation. Each source retains at most 400 dates. Cache hits, failed/stale reports and missing values do not create new observations. The deployed Firestore rules deny unmatched paths, so this collection is inaccessible directly to browser clients; preserve that boundary in any future rules change.

Instagram and Pinterest gain full-period count changes once both boundary dates are recorded: the date before the selected start and the selected final date. Shorter recorded spans appear only on the individual source, with their actual dates and a partial-period label; they never inflate the overview's selected-period change. Today’s observations are saved but excluded from completed-period growth. Before two completed dates exist, the UI says “Recording daily history.” These are latest-fetch observations, not guaranteed end-of-day counts. Collection runs when the dashboard fetches; days without a fetch remain missing, and pre-collection counts cannot be reconstructed. YouTube observations are retained for history without replacing its more accurate native growth metric. Storage failures leave live reports usable and do not claim successful collection. CSV includes completed-day `followersSnapshot` rows with the original fetch timestamp.

YouTube comparisons shift the available current date span back by the selected period length. Delayed final days are omitted from both sides and labelled “vs prior matched days”; per-source hover details give both date ranges. Empty comparison responses and comparison-request failures leave changes unknown while retaining the current report. The recent-day processing state is unchanged.

The client requests only `campaigns` and `campaigns.members`, with a separate creator-approved OAuth code flow. Patreon bundles the latter permission with access to member names and pledge details; disclose that bundle and obtain explicit consent before authorizing it. Leave the automatically generated, broader creator tokens unused. The reporting adapter requests only `patron_status`, `currently_entitled_amount_cents`, `is_free_trial` and `campaign_lifetime_support_cents`, plus campaign currency, aggregates in server memory, and never returns member identities, individual amounts or credentials. No member email, address, posting or webhook scopes are needed.

Register the reporting app under a different Patreon account from the campaign being reported. Patreon returned all creator scopes when Watch Club authorized its own app, despite the requested read-only scopes; the validator rejected that connection before reading member data or saving tokens. The separately owned app returned exactly the two approved scopes. Its owner profile need not be published. Do not relax scope validation to accept a creator token.

The dedicated `AKOGARE_PATREON_CONNECTION` secret holds the pinned campaign identity, app credentials and rotating read-only connection. The shared configuration contains only the secret pointer and non-secret campaign metadata. The function may access and add versions of this dedicated secret to persist rotation. A new token is saved before use, and exact scopes are checked on connection and renewal. A grant to a different creator, extra scopes or incomplete/duplicated membership pages never produces a complete breakdown.

The dashboard shows API patrons with access, active paid memberships excluding trials, active free trials, and memberships with declined payment status. These are current snapshots, independent of date selection; API patron totals must not be relabelled as all free and paid members. Lifetime member support sums the campaign-currency amount ever paid by each returned member, including former members. Every page and member amount must be complete, with valid currency and safe integer arithmetic; otherwise support stays unknown. This total is before fees, independent of selected dates, and must not be called net earnings, period income or a payout balance. Free-member totals, net earnings, payouts and historical net growth remain unavailable in this report. Memberships are separate from social follower/subscriber totals and content views. The Patreon platform filter shows membership summary cards and no fabricated daily activity chart. CSV snapshot rows have blank date ranges.

The creator-approved setup may use the HTTPS `patreonReportingCallback` endpoint on the existing Firebase project when desktop network access cannot reach Patreon's API. A temporary pending secret contains a random state hash, expiry and fixed redirect URI. The handler claims that state atomically in Firestore before exchanging a one-use authorization code, validates exact read scopes and the Watch Club campaign, and saves only the scoped connection. Callback pages never return credentials or member records. After setup the pending state is absent and the callback cannot initiate a grant or return reports. The local setup helper then records the non-secret source pointer; redeploy `projectAnalytics` to bind the latest shared configuration version.

The state/PKCE-protected HTTPS callback validates the exact permission, owner and shop before saving, and atomically prevents replay. Etsy item sales use paid receipts’ `subtotal`, after discounts and before refunds/fees, excluding tax and shipping, for orders created in the selected completed UTC dates. They are not labelled net profit or payouts. Confirmed buyer refunds and card-processing fees on those orders are separate metrics; unavailable or unrecognized refund states remain unknown. Processing fees come from Etsy Payments and do not include listing, advertising or all other shop charges. Payment fees can be reported in different currencies from the shop; totals are grouped and labelled by reported currency, with no implicit conversion or mixed-currency sum. CSV preserves each fee currency. Full net profit/account reconciliation stays in Etsy. Order pages, dates, ownership, currency and divisor must validate completely before sales can be shown; complete empty periods are genuine zeroes. Comparisons use the same order-cohort basis. The shop view emphasizes paid orders, item sales, refunds and available processing fees, with no follower statistic.

The workspace keeps monetary sources separate by currency and reporting basis. No grand total combines lifetime Patreon support with selected-period income. CSV rows carry currency; `lifetimeSupportCents` remains explicitly denominated in cents with blank period dates, while estimated revenue and net payment activity use major currency units and their actual dates.

YouTube monetary requests are separate from activity requests and require the exact channel-pinned reporting connection to include `yt-analytics-monetary.readonly`. A missing grant never triggers a monetary request. Reports request estimated revenue in USD, show the actual returned dates, preserve zero only when reported, and compare only identical shifted reporting-day sets. Missing, delayed or denied revenue never prevents other channel statistics from loading.

CineClub Stripe reporting uses a separately approved restricted live key with only Balance and Products read access, stored in `AKOGARE_STRIPE_REPORTING_CONNECTION`. It does not reuse checkout, account-deletion or other payment-management credentials. The main configuration holds a `stripeReporting` pointer and non-secret verified account/product metadata. The runtime identity may read only this dedicated reporting secret and does not need to rotate or add secret versions.

Stripe amounts are account-level net payment activity: payment and refund balance transactions after their transaction fees, for completed UTC dates. Payouts and other account adjustments are excluded, so this metric is not profit or a payout balance. The account and Cafe Regular product are pinned, and the complete live/archived product catalog must contain only that product; additional products require allocation review. Complete bounded pagination, USD currency, integer amounts and `net = amount - fee` are required. Website and iOS memberships paid on the website are counted once. Other app or website sales remain unavailable until their actual billing reports are connected; traffic alone cannot establish zero revenue.
