# Studio analytics

Open https://akogarecafe.com/dashboard (the GitHub Pages entry redirects to the existing hash router). The exact `akogarecafe.com` domain is authorized for Firebase Google sign-in, alongside the existing movieclub domain; the original domains were preserved.

Google workspace sign-in continues in the same tab at `https://ac-movie-club.firebaseapp.com/#/dashboard`. The dashboard is also hosted there, with its existing Firebase `authDomain` matching the page origin. This avoids the stalled cross-window callback observed in Chrome and the cross-origin storage dependency of redirect sign-in. The app handles `getRedirectResult` on return; it does not pass tokens through URLs. Both hosts call the same protected reporting function. Email/password login remains available on the cafe host.

The public site contains an empty dashboard shell. All shared reports require a Firebase ID token. The `projectAnalytics` callable checks the verified email against `allowedEmails` in the `AKOGARE_ANALYTICS_CONNECTIONS` Secret Manager secret, or a trusted `dashboardViewer` custom claim, before fetching or returning cached data. A legacy Gmail account with an unverified Firebase primary email must instead have a fresh Google sign-in: the function checks the token's Google subject against the server-side Google provider identity and its exact invited Gmail address. An unverified email or password sign-in alone never grants access. A Firestore user document cannot grant dashboard access. Only the owner's two existing Google accounts were initially allowlisted. Add invited readers deliberately through the secret or a server-admin custom claim; never broaden this to all authenticated accounts.

Provider credentials are stored only in that Firebase secret. No provider tokens, member records, private report snapshots or service-account keys belong in Git or static assets. Browser reporting OAuth uses a separate Firebase auth instance, so selecting a YouTube Brand Account does not replace the workspace login. Its transient redirect state uses tab-session storage and is cleared immediately on return, including the secondary Firebase session. The resulting Google access token and reports stay in memory and clear at sign-out, account change or page reload. Google reporting uses the same-tab redirect flow as workspace sign-in; another reporting redirect also ends previous in-memory reporting connections. A Google Analytics token can be reused for the website and iOS source selectors during that page session. The separately authorized server connections provide automatic reporting across visits; browser consent remains a temporary fallback.

The server also supports independently approved automatic Google reporting connections. `googleReportingClient` holds a dedicated OAuth client in the dashboard's Google project, `ga4OAuth` holds its Analytics refresh connection, and `youtubeReporting` holds channel-specific refresh connections. These take precedence over the older YouTube connections without editing or replacing publishing credentials. Provision them only after explicit consent to persistent read-only access. Use authorization code flow with PKCE, a random state checked on return, and a loopback callback for the desktop client. Validate the exact read-only scopes and the expected property/channel before saving a connection. Keep callback codes and tokens out of URLs printed in logs, source files, browser storage and static assets. When accessing Secret Manager directly, omit request and response bodies from diagnostic logging.

The Analytics connection requests only `analytics.readonly`. Each YouTube connection requests only `youtube.readonly` and `yt-analytics.readonly`; publishing or editing scopes are not needed. The function refreshes each connection once per reporting request, shares the Analytics token across its mapped sources, and returns only report data plus an `automatic` connection marker. The source details explain automatic reporting only when the server confirms that connection. A failed YouTube period report retains freshly fetched channel totals as limited access, with the period metrics unknown. After changing the secret, deploy the isolated function again so it uses the new version, then verify reports after a fresh signed-in page load.

## Reporting semantics

Dates cover 1, 7, 28 or 90 completed UTC calendar dates, ending yesterday. The default is 28 days. Last 1 day is yesterday’s calendar date, not a rolling 24-hour or realtime report; its chart uses a centered point. A visible notice explains that daily numbers are provisional and YouTube can take 48–72 hours to process. Empty one-day YouTube reports keep period metrics unknown and show a waiting state while preserving current channel totals; explicit reported zeroes remain zero. Weekly and 28-day views are more useful for judging trends. Providers apply their own property/reporting timezone to those dates; cross-provider day boundaries may differ. YouTube and Instagram content views are separate from Pinterest impressions, website sessions, iOS active users and lifetime totals. The activity chart initially chooses a metric with available daily reports, falls back to a metric for the selected platforms when data is still collecting, and preserves an explicit user choice. A collecting source has matching visible and accessible empty-chart messages. Points use actual calendar spacing within the selected reporting period. A configured collection start date bounds requests and suppresses unavailable prior-period comparisons; periods ending before collection starts have no fabricated zero metrics. Missing values remain null/unknown; true zero remains zero. Coverage labels identify partial totals. Audience counts are a sum of channel followers/subscribers, not deduplicated people. Comparisons appear only with complete current and previous coverage. The backend has a five-minute, authorized-workspace cache. The page refreshes while visible, independently retains errors, and clearly marks retained data stale on failure. A date/account change clears old period data.

CSV exports contain only the visible sources' available metrics and are generated on an explicit click. Snapshot metrics have blank period dates. No private export is uploaded to the repository.

## Server deployment

`firebase.analytics.json` defines an isolated `akogare-analytics` codebase. Deploy only that codebase to `ac-movie-club`; do not deploy/delete the existing club functions. Runtime: Node 22, first generation, us-central1, maximum three instances, 60-second timeout. The caller endpoint is fixed in `src/components/Dashboard/api.js`.

Install server libraries with `npm ci --prefix analytics-functions`, test with `npm test --prefix analytics-functions`, and deploy with `firebase deploy --config firebase.analytics.json --only functions:akogare-analytics --project ac-movie-club --non-interactive`. Secrets are configured separately with the supported Firebase CLI stdin mechanism; never put their values in command arguments or tracked files.

The site's normal `main` branch workflow tests and publishes the client to GitHub Pages. Publish the same tested build to the secure workspace with `firebase deploy --config firebase.analytics.json --only hosting --project ac-movie-club --non-interactive`. The Firebase hosting site had no deployed public app before this dashboard. Its pages have an `X-Robots-Tag: noindex, nofollow` header. Changing server source also requires the separate Firebase functions deployment above. A Git push alone does not update the function or Firebase-hosted client.

## Period changes

Summary cards, project cards and channel rows show signed count changes and percentages versus the previous equal-length period. Each change uses only sources with both current and previous metrics; partial comparison coverage is labelled separately from total-metric coverage. A zero baseline still shows the absolute change but no undefined percentage. Stale or failed sources never contribute a change. Lifetime totals never receive period comparisons. YouTube audience growth is subscribers gained minus lost during the reported days, not a difference between rounded subscriber snapshots. Instagram/Pinterest growth remains unknown without history. Product account growth counts creation timestamps within the selected dates; it describes new accounts, not net growth after deletions.

YouTube comparisons shift the available current date span back by the selected period length. Delayed final days are omitted from both sides and labelled “vs prior matched days”; per-source hover details give both date ranges. Empty comparison responses and comparison-request failures leave changes unknown while retaining the current report. The recent-day processing state is unchanged.

## Patreon membership

Watch Club Patreon is https://www.patreon.com/c/AkogareWatchClub and belongs to the existing Watch Club project. Its source ID is `watch-patreon`. The client requests only `campaigns` and `campaigns.members`, with a separate creator-approved OAuth code flow. Patreon bundles the latter permission with access to member names and pledge details; disclose that bundle and obtain explicit consent before authorizing it. Leave the automatically generated, broader creator tokens unused. The reporting adapter requests only `patron_status`, `currently_entitled_amount_cents` and `is_free_trial`, aggregates in server memory, and never returns member identities, individual amounts or credentials. No member email, address, posting or webhook scopes are needed.

The dedicated `AKOGARE_PATREON_CONNECTION` secret holds the pinned campaign identity, app credentials and rotating read-only connection. The shared configuration contains only the secret pointer and non-secret campaign metadata. The function may access and add versions of this dedicated secret to persist rotation. A new token is saved before use, and exact scopes are checked on connection and renewal. A grant to a different creator, extra scopes or incomplete/duplicated membership pages never produces a complete breakdown.

The dashboard shows API patrons with access, active paid memberships excluding trials, active free trials, and memberships with declined payment status. These are current snapshots, independent of date selection; API patron totals must not be relabelled as all free and paid members. Free-member totals, earnings, payouts and historical net growth remain unavailable in this report. Memberships are separate from social follower/subscriber totals and content views. The Patreon platform filter shows membership summary cards and no fabricated daily activity chart. CSV snapshot rows have blank date ranges.

The creator-approved setup may use the HTTPS `patreonReportingCallback` endpoint on the existing Firebase project when desktop network access cannot reach Patreon's API. A temporary pending secret contains a random state hash, expiry and fixed redirect URI. The handler claims that state atomically in Firestore before exchanging a one-use authorization code, validates exact read scopes and the Watch Club campaign, and saves only the scoped connection. Callback pages never return credentials or member records. After setup the pending state is absent and the callback cannot initiate a grant or return reports. The local setup helper then records the non-secret source pointer; redeploy `projectAnalytics` to bind the latest shared configuration version.
